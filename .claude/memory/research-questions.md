# 研究方向的开放问题

## 🔴 高优先级（已决策）

### Q1: 项目的核心定位是什么？
**决策（2026-06-27）：AB 组合**
- ✅ 专注于理论研究（OS启发的架构创新，验证代理为核心）
- ✅ 但也要接入真实LLM来展现能力（Demo + 实验）

**影响**：
- 核心架构保持研究导向，不追求生产级可靠性
- 需要设计真实LLM集成层（作为可选feature，非核心）
- 验证代理可以继续用MockAgent
- 新增实验性验证代理展示真实LLM行为

### Q2: "天马行空的想法"具体是什么？
**决策（2026-06-27）：OS底层创新（具体方向待澄清）**
- ✅ 与OS有关的创新，但用户的具体想法需要进一步澄清
- ❌ 不是跨Agent学习、自我修改代码、情感建模等泛化能力
- ❌ 不是Agent网络拓扑、动态主权协商等应用层创新

**待澄清**：用户心中的OS底层创新具体指什么？
- 可能的方向：
  - Agent内部的真实OS式微内核（不只是概念，而是真实的内核态/用户态隔离）
  - Agent间的OS式IPC（进程间通信）创新
  - Agent的"文件系统"（Agent如何持久化和共享知识）
  - Agent的"设备驱动"（如何统一抽象工具/能力）
  - Agent的"中断机制"（如何响应外部事件）

**影响**：需要与用户深入讨论，确定具体的RFC-004设计方向

### Q3: 主权系统与真实 LLM 的关系？
**决策（2026-06-27）：C（实验性）**
- ✅ Trust Score 影响推理参数（temperature、top_p 等）
- ✅ 实验性探索，非生产级设计

**影响**：
- 需要设计 Trust Score → 推理参数的映射机制
- 可能需要实验不同的映射策略
- 需要记录实验结果，验证"真主权"的效果

### Q4: RFC-002 调度系统的优先级？
**决策（2026-06-27）：A（但延后实施）**
- ✅ 要实施
- ✅ 但不是本次任务，也不是下次任务
- ✅ 可能是第三个或更后面的任务

**影响**：
- 当前优先级：Q2的OS底层创新 > RFC-002调度系统
- RFC-002可以在核心架构稳定后实施

### Q5: 目标社区和受众？
**决策（2026-06-27）：三个受众群体**
- ✅ Agent开发者（关注如何构建主权代理）
- ✅ AI使用者（关注如何使用主权代理）
- ✅ OS研究者与开发者（关注OS哲学在AI中的应用）

**影响**：
- 文档需要覆盖三个层次：
  1. 理论层（OS哲学、架构创新）→ OS研究者
  2. 实践层（如何构建主权代理）→ Agent开发者
  3. 应用层（如何使用主权代理）→ AI使用者
- README和文档需要分层组织
- 示例需要覆盖不同受众的需求

## 🟢 低优先级（锦上添花）

### Q6: 内存层的持久化策略？
**现状**：MemoryTool 使用 in-process HashMap，进程重启后丢失。

**问题**：
- 是否需要持久化内存？
  - A) 不需要（研究项目，in-process 足够）
  - B) 需要（生产化必备，考虑 SQLite、Redis、文件存储）
  - C) 可选（提供 trait，用户自行实现）

### Q7: 多 Agent 拓扑的探索方向？
**现状**：当前支持 Agent 间通信，但拓扑结构未深入探索。

**问题**：
- 是否想探索特殊的 Agent 网络拓扑？
  - A) 层级结构（Supervisor → Worker 树）
  - B) 对等网络（Agent 间直接协商）
  - C) 动态拓扑（Agent 可动态加入/离开网络）
  - D) 暂不探索（先完善单 Agent 能力）
